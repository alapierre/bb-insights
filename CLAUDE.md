# Project Name

bb-insights it is a short name from BitBucket Insights

# Project Overview

This project is an open source command line application written in Go.

Its purpose is to bridge a missing capability in **Bitbucket Cloud** by publishing software quality and security reports to **Bitbucket Code Insights** using the official Bitbucket REST API (https://support.atlassian.com/bitbucket-cloud/docs/code-insights/).

Bitbucket Cloud provides an excellent pull request experience, but unlike competing platforms it lacks native integrations for many common report formats such as Go coverage or Trivy SARIF.

This project aims to fill that gap.

The application does **not** perform any analysis itself.
Instead, it consumes reports generated by existing tools and publishes them in a form that Bitbucket Cloud understands.

The project is intended to become a lightweight, reliable and extensible reporting layer for Bitbucket Cloud.

---

# Initial Scope (MVP)

The first public version supports three report types:

- Go unit test reports
- Go coverage reports
- Trivy security scan reports

Go test execution is expected to use:

```bash
gotestsum \
  --format pkgname \
  --junitfile test-results/unit-tests.xml \
  -- \
  -coverprofile=coverage.out \
  ./...
```

This produces two independent inputs:

- `test-results/unit-tests.xml`
- `coverage.out`

Trivy is expected to generate:

```bash
trivy image .../...:${BITBUCKET_TAG#v}
```

# Goals

The application should:

- publish Bitbucket Code Insights reports
- publish useful metrics
- publish annotations whenever possible
- provide deterministic output
- produce meaningful error messages
- integrate naturally with Bitbucket Pipelines
- be usable as a Bitbucket Pipe (`pipe: docker://...`), not just as a
  binary installed and invoked manually in a script step
- remain lightweight and dependency-light

The application should never attempt to replace scanners or testing tools.

Its responsibility starts after those tools have already produced their reports.

---

# Non Goals

The application is not responsible for:

- executing unit tests
- generating coverage
- running Trivy
- fixing vulnerabilities
- replacing existing analysis tools

It only transforms existing reports into Bitbucket Code Insights.

---

# Long-Term Vision

The architecture should allow adding support for additional report formats without modifying existing implementations.

Potential future parsers include:

- golangci-lint
- Semgrep
- Checkov
- Hadolint
- CodeQL SARIF
- Dependency Check
- CycloneDX
- SPDX
- JUnit variants
- other SARIF producers

Each parser should be implemented independently.

# Architecture

The application should be organized into three logical layers.

## Parser

Responsible for reading external report formats.

Examples:

- coverage.out
- JUnit XML
- SARIF

Every parser converts its input into a common internal model.

---

## Internal Model

The internal model should not depend on any particular report format.

It should represent concepts such as:

- Report
- Summary
- Metric
- Annotation
- Severity
- Location

This model is the contract between parsers and publishers.

---

## Publisher

Responsible only for publishing the internal model.

Initially the only publisher is:

- Bitbucket Cloud Code Insights

The publishing layer should not know anything about coverage.out, SARIF or XML.

# Supported Reports

## Go Test Report

Source:

```
test-results/unit-tests.xml
```

Generated by:

```
gotestsum --junitfile ...
```

The parser should extract:

- total tests
- passed tests
- failed tests
- skipped tests
- package information
- execution time

The Bitbucket report should expose useful metrics summarizing the test execution.

---

## Go Coverage Report

Source:

```
coverage.out
```

Generated by:

```
go test -coverprofile=coverage.out
```

The parser should calculate:

- overall coverage
- coverage per file
- number of covered files

The Bitbucket report should contain metrics.

Future versions may optionally generate annotations for files below a configurable coverage threshold.

---

## Trivy Security Report

Source:

```
trivy.sarif
```

Generated by:

```
trivy --format sarif
```

The parser should extract:

- vulnerabilities
- severity
- rule id
- package
- CVE
- message
- file location (if available)

The Bitbucket report should expose metrics:

- Critical
- High
- Medium
- Low

Whenever SARIF contains location information, annotations should be created.

---

## JaCoCo Coverage Report

Source:

```
jacoco.xml
```

Generated by:

```
JaCoCo Maven/Gradle plugin (jacoco:report / jacocoTestReport)
```

The parser should calculate:

- line coverage
- branch coverage
- number of packages

The Bitbucket report should contain metrics.

Future versions may optionally generate annotations for files below a configurable coverage threshold, matching the Go coverage report.

# Command Line Interface

The CLI should remain simple and discoverable.

Examples:

```bash
bb-insights publish tests \
    --junit test-results/unit-tests.xml
```

```bash
bb-insights publish coverage \
    --input coverage.out
```

```bash
bb-insights publish trivy \
    --input trivy.sarif
```

```bash
bb-insights publish jacoco \
    --input jacoco.xml
```

The command structure may evolve but should remain consistent.

A second invocation mode exists for Bitbucket Pipes: when started with no
arguments at all (which is how `pipe: docker://...` invokes a container,
configuring it only through environment variables), the CLI picks the
subcommand from `BB_INSIGHTS_REPORT_TYPE` instead. Every subcommand's
flags must therefore have an env var fallback (as the existing ones do),
and any new subcommand should support this mode the same way.

# Design Principles

The project should:

- follow idiomatic Go
- use minimal dependencies
- keep packages cohesive
- separate parsing from publishing
- avoid unnecessary abstractions
- favor composition over inheritance
- remain easy to extend
- remain easy to test

Readability is more important than cleverness.

---

# Error Handling

Every error message should explain:

- what failed
- why it failed
- how the user can fix it

Avoid generic error messages.

---

# Testing

Unit tests should cover:

- report parsers
- conversion into the internal model
- Bitbucket payload generation

HTTP communication should be tested using mock servers.

Production Bitbucket Cloud should never be required for automated tests.

---

# Performance

The application should comfortably process:

- large Go projects
- large SARIF reports

Avoid unnecessary memory allocations.

Streaming should be preferred whenever practical.

---

# Supply Chain & Release Security

These are standing project policies, not a one-off task - don't remove or
weaken them while refactoring CI/release workflows without discussing it
first:

- Every release publishes a SBOM (for the binary and the Docker image) and
  a build provenance attestation (for the binary and the Docker image),
  verifiable with `gh attestation verify`.
- Dependencies are monitored continuously, not just at release time: new
  CVEs can appear for a dependency that hasn't changed in months, so
  vulnerability scanning runs on push/PR/schedule (not tied to releases),
  and Dependabot keeps `go.mod`, GitHub Actions and the Dockerfile base
  image up to date.
- New GitHub Actions workflows/jobs should request the minimum permissions
  they actually need.
- Security vulnerabilities are reported through GitHub's private
  vulnerability reporting (see `SECURITY.md`), never as a public issue.

# AI Development Guidelines

When implementing new functionality:

- work in small incremental steps
- write tests together with production code
- document exported APIs
- avoid unnecessary interfaces
- avoid premature optimization
- keep the CLI intuitive

Every new report format should be implemented as an independent parser.

Existing parsers should not require modifications when new formats are introduced.
